# Implementation Plan: Todo Priority Levels

**Branch**: `001-todo-priority` | **Date**: 2026-09-18 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-todo-priority/spec.md`

## Summary

Extend the existing Todo API to support a `priority` attribute on every Todo item. Priority is restricted to exactly four levels — `urgent`, `high`, `medium`, `low` — enforced at the service boundary. `medium` is the default when a consumer omits the field. The feature adds priority to creation and update requests, exposes it in all responses, and adds priority-based filtering to the list endpoint. A new Alembic migration backfills legacy rows with `medium`. No existing endpoints are removed or renamed; this is a backward-compatible additive change per Constitution Principle V.

**Target Platform**: Linux server (FastAPI / Uvicorn process)

**Project Type**: REST web service (single-project layout under `src/project_qwe/`)

**Performance Goals**: No new performance requirements; priority field adds negligible overhead. Existing response-time envelope preserved (SC-006).

**Constraints**: Backward-compatible API change only (Constitution Principle V). No new version prefix. All changes must pass `uv run pytest`. Alembic migration must be autogenerated and include a downgrade path.

**Scale/Scope**: Single Todo resource with existing CRUD + pagination. Priority is a new scalar column on the `todos` table; no new tables, no new relationships.
