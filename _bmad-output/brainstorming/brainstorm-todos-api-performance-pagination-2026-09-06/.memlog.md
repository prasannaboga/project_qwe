- (technique) started Role Playing
- (idea) Page-based offset pagination supporting page and per_page parameters with a server-side max limit cap
- (idea) Sorting mechanism using query parameter format sort=keyword:direction (e.g. sort=due_at:asc)
- (idea) Strict allowlist of sortable fields restricted to indexed columns (title, due_at, created_at, updated_at) and valid directions
- (idea) Add database indexes specifically for fields commonly filtered or sorted
- (idea) Strict validation rejecting unsupported sort/direction requests and blocking arbitrary SQL expressions in filter/sort
- (technique) started Reverse Brainstorming
- (insight) Deep offset hammering (huge page/per_page) and repetitive heavy sorting causes severe CPU, memory, and I/O exhaustion
- (insight) Concurrent mutations during offset traversal cause phantom duplicates or skipped records across page boundaries
- (idea) Enforce maximum page depth cap in addition to per_page limit to prevent deep offset table scanning
- (idea) Use cursor-based (keyset) pagination or guaranteed stable tie-breaker ordering (e.g. secondary sort on ID) to eliminate drift
- (technique) started First Principles Thinking
- (idea) Minimal response payload returning items and has_next_page flag (e.g. fetch limit+1 to check next page existence with zero extra queries)
- (idea) Eliminate mandatory COUNT(*) queries; make total count an optional parameter or calculate/cache separately
- (decision) Prioritized Must-Have: A (page/per_page with hard caps), B (strict sort allowlist), C (deterministic tie-breaker ordering on ID), D (lean items + has_next_page envelope via limit+1), E (indexes on sort/filter columns). Won't-Have-This-Time: F (total count calculation), G (cursor-based pagination)
- (insight) Synthesis: The 5 Must-Haves form a self-reinforcing, zero-overhead baseline: offset pagination is made safe by max depth caps, stable tie-breaker ID ordering stops drift without cursor complexity, limit+1 eliminates count queries, and indexes back the sort allowlist.
