### God-Class / Size Growth

**Source:** `wc -l src/project_qwe/services/todo_service.py` → **414 lines**. Git range net churn: +254 lines added to the file across 9 commits.

**Observation:** `todo_service.py` is the heaviest production file in the epic's output at 414 lines. It grew by +254 net lines across the range, absorbing new service methods for:
- `search_todos` (Story 1.2)
- `get_active_todos` (Story 1.3)
- A summary/overdue computation (`get_todo_summary_markdown`) embedded directly in the service file (Stories 1.3–1.4)

The file is not a god-class today but is approaching a size where the next epic's additions will make it one. All 10+ public functions serve a single entity (`Todo`) with a coherent concern boundary.

**Disposition:** defer. No immediate refactor required. Propose a process lesson: set a 400-line soft cap on service files; any story that would push past it should consider splitting or helper extraction before implementation.

### Duplication Map

**Source:** reviewed `tools.py` (304 lines), `resources.py` (168 lines), `prompts.py` (189 lines).

**Observation 1 — isError formatting:** Each tool in `tools.py` constructs MCP error results using a consistent inline pattern (returning a `ToolResult` / `TextContent` with `is_error=True`). No reimplementation between stories; Story 1.2 established the pattern and Stories 1.3–1.4 followed it for resources and prompts respectively.

**Observation 2 — Summary logic inlined in service:** `get_todo_summary_markdown` renders a markdown string inside `todo_service.py` (lines 374–414). Rendering logic (formatting bullet lists, writing markdown headers) sits in the service rather than a dedicated formatter. This is a mild concern — presentation logic in the service layer — but does not violate the project's stated conventions (which prohibit business logic in route handlers, not presentation in services).

**Disposition:** Observation 2 → defer. Record as a candidate for extraction in a future refactor if a second markdown-rendering function appears in the same file.

### Pattern Divergence

**Source:** Reviewed commit subjects and test file structure across the epic range.

**Observation 1 — Missing story IDs in commit subjects:** 8 of 9 commits lack a story-ID prefix (e.g., `feat(1-2):` or `[1.2]`). Only `2aefe56` includes `spec-1-1` in the subject. The project has no enforced commit-message convention, so this is not a violation — but it made git_evidence.py's story attribution return `stories: []` for most commits, reducing traceability.

**Observation 2 — Duplicate story implementation commits:** Stories 1.2 and 1.3 each have two implementation commits (e.g., `0d357f8` and `49c320b` for Story 1.2; `5953bc8` and `b39c5e9` for Story 1.3). This pattern was caused by the review-and-fix loop during build-auto runs. Not a defect in the code, but a signal that the stories needed significant rework post-initial-implementation.

**Observation 3 — SSE test flakiness (intermittent):** `test_sse_e2e_discovery_and_operations[asyncio]` failed on the first isolated run (`1 failed, 11 passed`) but passed in the subsequent full-suite run (`174 passed`). The SSE test uses a real uvicorn daemon thread on an ephemeral port — this is timing-sensitive. No consistent failure reproduced across three runs.

**Disposition:**
- Obs 1 → defer. Propose a process lesson: add story-ID prefix convention to AGENTS.md for future epics.
- Obs 2 → accept as-is. Two-commit pattern per story is consistent with the build-auto review loop.
- Obs 3 → defer with monitoring. The SSE e2e test is timing-dependent. If it fails consistently in CI, the fix is to add a startup-ready poll instead of a fixed sleep before the client connects.
